## 申し送り(段をまたぐ決定)

### Q1 の着手条件 — 常時SSE接続の「止め方」を決める(2026-08-27、Q0レビュー minor-2 由来)

Q0 で SSE 接続をプロセススコープへ移した結果、**止める経路がプロセス終了しか無い**。
`OpenCodeEventStream` に `stop()` が無く、`AppContainer.scope` を誰もキャンセルしない。
`OpenCodeEvents` の再試行は上限8秒のバックオフで**無限に回る**。実害:

- **パスワードを間違えて保存すると、health は401を表示する一方で SSE は永久に再接続を試み続ける。**
  旧実装ではチャット入室中だけの挙動だった
- バックグラウンド/画面OFF中も接続を保持する(Doze で大半は止まるが、ライフサイクル配慮はゼロ)

Q0 では直さない。**ライフサイクル設計は Q0 の「挙動を変えない」枠を超える**ため。
Q1 の実装に入る前に、以下を決めて `API_CONTRACT.md` ではなく本文書に記録すること:

- 401/403 を「一時的な切断」と扱わない(再試行を止めて状態に出す)
- プロセスがバックグラウンドにある間の扱い(切る / 保つ / バックオフを伸ばす)
- `stop()` を誰が呼ぶのか(呼ばないなら、なぜ呼ばなくてよいのか)

**2026-08-27 のE2Eで実測が付いた(所見Q0-2)**: アプリをバックグラウンドへ回すと実際に
`sseClients` は **0 に落ち**、復帰時に「⚠ イベントストリーム再接続中…」を経て再接続する。
つまり「常時1本」は**画面出入りに対しては成立しているが、プロセスのバックグラウンド化には
成立していない**。Q1 の実行状態バッジが「一覧を開いている間の常時更新」で足りるなら現状で良い。
足りないなら設計が要る。**どちらで足りるのかをQ1の実装前に決めること。**

## Q1 着手条件の裁定(2026-08-27、オーケストレータ)

2つの着手条件を、**1つの整合した設計**として閉じる。Q1 の実装スコープに含める。

### 決定1: SSE は「フォアグラウンドの間だけ」保つ

現状(バックグラウンドで切れ、復帰で再接続)を**追認する**。切らない方向へは直さない。
理由: Q1 の実行状態バッジが要求するのは「**一覧を見ている間、状態が正しいこと**」であり、
見ていない間の更新は要らない。バックグラウンドで接続を保つのは電池と Doze の両方に逆らう。

ただし**「常時1本」の意味を文書上も正しくする**: `OpenCodeEventStream` の doc と QUALITY_PLAN §5 Q0 の
「アプリ起動中は常時1本」は、実際には「**プロセスがフォアグラウンドにある間は常時1本、画面の出入りでは切らない**」
である。Q0 が満たしたのは後者で、前者は満たしていない。**満たしていないものを満たしたと書かない。**

### 決定2: 状態はイベント列ではなくサーバーの現在値で初期化する

購読者ゼロの窓(replay=0)は **replay で塞がない**(Q0 の判断を維持。回転で解決済みダイアログが蘇るため)。
代わりに **一覧が購読を開始する時点で `GET /session/status` を1回取得**し、以後の `session.status`
イベントで更新する。**再接続のたびにも取り直す**こと — 切れている間のイベントは失われており、
イベント列だけでは状態が古いままになる。これは Q0 実装がコード内に残した申し送りと同じ結論。

### 決定3: 401/403 は「一時的な切断」として扱わない

誤ったパスワードを保存すると、health は 401 を表示する一方で **SSE は永久に再接続を試み続ける**
(Q0 レビュー minor-2)。認証失敗は再試行で解決しない。**再試行を止め、状態に出す。**
`OpenCodeEventStream` に停止経路(`stop()`)を用意し、接続先変更・認証失敗・フォアグラウンド離脱で呼べるようにする。

### Q2 への申し送り — `SessionStatus.retry` の `action`(2026-08-27、Q1レビュー minor-7)

spec の `SessionStatus` の `retry` は `action` を任意で持ち、その required は
`reason` / `provider` / `title` / `message` / `label` の5項目。Q1 の `SessionStatusDto` は
`action` を持たない(`ignoreUnknownKeys` で落ちないので**Q1では欠陥ではない**)。
**Q2 の retry バナー(QUALITY_PLAN §5 Q2 スコープ6)は `action` を使う可能性が高い**ので、
Q2 の契約first手順でここを埋めること。

## 常設ルール — エミュレータは共有資源である(2026-08-27、Q1 E2E担当の寸止めから)

Q1 のE2E担当が完了後に再起動し、`sseClients` が 0 のまま busy バッジも出ないのを観測した。
**「アプリのSSEが死んで再接続しない」という欠陥に見えた。** 報告する前に裏を取ったところ:

- dump に出ていたのは自分が測った画面ではなかった(`desc="reasoning:expanded"` /
  `text="💭 思考"` / markdown見出し = **Q2 の作業画面**)
- `dumpsys package` の `lastUpdateTime` が自分のインストール時刻より後で、APKのサイズも違った
  (11,050,934 → 14,689,516 バイト)
- `netstat` に**自分が起こしていない 4099 のスタブ**が居た

**測定器が自分の足元で入れ替わっていた。** アプリは別のスタブを見ており、自分が 4098 に流した
`session.status(busy)` は届きようがなかった。P5 で「存在しないアプリ欠陥を報告しかけた」のと同じ形である。

したがって以後、**実機を触るエージェントは全員**:

1. **測る前に、いま入っているAPKが自分のビルドかを確かめる**(`dumpsys package` の `lastUpdateTime` と
   ローカルAPKのサイズ/時刻を突き合わせる)。仮定しない。Q1のE2E担当は実際に**自分でビルドし直して
   `install -r` してから測った**。これを既定の手順とする
2. **アプリの接続先が自分のスタブかを確かめる**(ポート番号まで)。`__stub/stats` が自分の投げた物を
   反映しているかを、測定の**前**に1回確認する
3. **完了報告後に観測した異常は、まず「自分が測っていた対象がまだそこに在るか」を疑う。**
   段の完了報告に書いた「最終状態」は、**その時点の記録**であって現在ではない

**オーケストレータの責任**: 実機を使う段を重ねて走らせないこと。Q1のE2Eが完了したと判断して
Q2実装を派遣したが、E2E担当のプロセスはまだ生きていた。**「報告が返った」と「もう触らない」は別**である。

## ハーネスの欠陥 — スタブの abort が実サーバーと違う(2026-08-27、Q2実装が実物serveで発見)

Q2 が実物 serve(1.18.21)に対して abort を実測した結果:

```
+ 6592ms HTTP POST /session/{id}/abort -> 200 body=true
+ 6592ms SSE session.status {"type":"idle"}
+ 6592ms SSE session.idle
```

**実物 serve は abort で `session.idle` を流す。** 一方 `e2e-stub` の abort は世代番号で黙って止めるだけで、
何も流さない。**両者は食い違っている。**

帰結として、**P4ゲート②「abort押下で `eventsSent` が停止し8秒後も不変」は、実サーバーと異なる
スタブ挙動を正としていた**。P4 は「サーバー側が止まったこと」しか見ておらず、
**UIが復帰するかを測っていなかった**ため、Q0-1(abort後もUIが応答中のまま)が P4→P5→Q0 と
3段にわたって残った。

- スタブ側は `STUB_ABORT_IDLE=1`(**既定オフ**)で実サーバー相当にできる。
  既定を変えると P4/Q0 の既存証跡が崩れるため、Q2 実装は既定を変えていない。**この判断は妥当**
- **P4ゲート②の文言そのものを見直す必要がある。** → Q6「回帰一式」で、既定を実サーバー相当へ
  切り替えたうえで P4 を測り直し、ゲート文言を「サーバーが止まる」から
  「**サーバーが止まり、かつUIが復帰する**」へ改めること

**一般則**: スタブは「機構を安く検証する道具」であって「契約の定義」ではない。
**スタブの挙動をゲート条件に書き写した瞬間、スタブの誤りが正解になる。**
以後、スタブで閉じるゲートは「この挙動は実物で確認済みか」を明示すること。

### ~~Q3以降への申し送り~~ → **Q2 へ差し戻し(2026-08-27、オーケストレータの判断ミスを撤回)**

Q2 実装が「チャットの busy がサーバー現在値で初期化されない」を未解決事項として正しく報告し、
**私はそれを Q3 送りにした。この判断は誤りだったので撤回する。**

Q2 レビューが指摘したのは同じ箇所のより深い症状である: 送信中に**背面へ回すと `sseClients` は 0 に落ち**、
その間にサーバー側が完了して流した `session.idle` は**購読者ゼロで消える**。復帰後に再接続しても
更新されるのは一覧のバッジだけで、**チャットは `busy=true` のまま入力欄が永久に disabled になる**。
帯は1本も出ず、画面はどこも壊れて見えない。一覧へ戻って入り直す以外に復帰経路が無い。

これは RUN_PLAN「決定2」(**再接続のたびにも取り直すこと**)の違反であり、
`OpenCodeEventStream.kt` のコメントにも同じ規則が書かれている。Q1 は一覧に対して実装済みで、
**Q2 が新設した状態機械にだけ未実装**だった。**入力欄の状態と帯は Q2 が所有する面**なのでスコープ外ではない。

**教訓**: 実装者が「スコープ外」と申告した項目を、**申告のまま次段へ送ってはならない**。
それが**現在の段が所有する面の欠陥**でないかを、オーケストレータが判定すること。
実装者はスコープの境界を機能名で見るが、欠陥は面で決まる。

### 決定 — `DELIVERY_FAILURE` 帯は「現状到達不能」のまま残す(2026-08-27、Q2 E2E所見Q2-2)

### 不具合1 —— `PtyUi.actionError` が端末を跨いで残留する

**症状(E2E の実測)**: サーバー停止中に resize が失敗して帯が立つ → サーバー復旧 →
一覧へ戻って新しい PTY を起動 → **健全な端末に古いサーバーエラーが出たまま残る。**
5端末・サーバー再起動3回を跨いで再現。

**原因は申し送りの推測どおり**だった。`closeTerminal()` / `open()` が `terminal` だけを
初期化し、`actionError` は `PtyUi` 直下の別プロパティとして居残る。

**直し方は2枚重ねにした。** どちらか片方では閉じないため:

1. **切り替え時に明示的にクリア** —— `closeTerminal()` と `open()` が `actionError = null` を置く
2. **状態を PTY ごとにスコープ** —— `actionError: String?` を
   `PtyActionError(ptyId: String?, message: String)` に変え、**出す/出さないの判定を
   純関数 `ptyActionErrorMessage(error, pane, openPtyId)` にだけ置いた**

1 だけでは足りない理由が**測って分かった**: `resize` の `PUT /pty/{id}` は非同期で、
**端末を切り替えた後に失敗して返ってくる経路がある**。そのとき状態を書くのは
`open()` より後なので、クリアは間に合わない。逆に 2 だけでは、
ユーザーが「閉じる」を押していないエラーが状態に溜まり続ける。

**ついでに閉じた穴**: 帯は端末の窓にしか無く、**一覧の行の「終了」(`DELETE /pty/{id}`)が
失敗しても、どこにも出ないまま次に開いた端末で初めて姿を現していた**。
帯を `PtyActionErrorBand` として切り出し、一覧の窓にも置いた(`content-desc` は同じ
`pty-action-error`。一度に描かれるのは片方の窓だけなので dump からの引用は変わらない)。

### 不具合2 —— 短い行と長い行が同じ `ScrollState` を共有すると横スクロールが死ぬ

**申し送りの診断は正しかった。** 自分で読んで確認した機序:

`Modifier.horizontalScroll` の layout は、**測るたびに `scrollState.maxValue = 内容幅 - 表示幅`
を書き込む**。Q7(差分)・Q8(ファイル)・Q9(端末)は3画面とも**1つの `ScrollState` を
全行の `horizontalScroll` に渡していた**ので、**N 個のノードが1つの状態を取り合い、
最後に測られた行の値だけが残る**。短い行(内容幅 ≦ 表示幅)が表示窓に1つでも入れば
その行が `maxValue = 0` を書き、`ScrollState` は `value` も 0 へ丸める ——
**長い行が同じ画面に出ていても横に1pxも動かない。**

全行が長ければ症状が出ない。**Q7/Q8 で露見しなかったのはそのため**で、
短い行が普通に混ざる端末で初めて出た。**Q9 固有の退行ではない。**

**共通部品にした**(`ui/LineScroll.kt`)。「最後に測られた行が勝つ」を
**「表示窓に出ている行の最大幅が勝つ」**に変える:

- 各行は `Modifier.lineScrollContent(state, key)` で**幅の制約を外して測り**、
  自分の内容幅を `state` に預けるだけ。スクロール量は持たない
- 表示窓は `Modifier.lineScrollWindow(state, "diff-hscroll")` でジェスチャーと計器を持つ
- `maxValue` は `widths.values.maxOrNull() - viewportWidth`(負にしない)

**計器の形は変えていない** —— `<key>:<現在値>/<最大値>` のまま。
変えると過去段の E2E 手順が読めなくなる。3画面(`diff-hscroll` / `file-hscroll` /
`pty-hscroll`)すべてを置き換えた。

**行キーは `LazyColumn` の item key と同じ物を使う。** 別々の鍵を作ると、
行が表示窓から出ても幅が残り、**居ない行が到達範囲を広げ続ける**。
端末は `reverseLayout` なので、**添字ではなく本物の行番号から鍵を作る**
(添字だと出力が伸びるたびに同じ鍵が別の行を指す)。
